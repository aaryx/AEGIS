## 1. SOP 1: Zero-Downtime Certificate Rotation

### 1.1 Scope
Applies to PostgreSQL, Redis, and OpenSearch TLS certificates.

### 1.2 Prerequisites
- New X.509 certificate and private key generated and signed by the corporate Root/Intermediate CA.
- Verification that SAN extensions include all cluster DNS names and IPs (`DNS:postgres.internal`, etc.).
- Proper file permissions: private key must be `chmod 600`, certificate `chmod 644`.

### 1.3 Execution Steps

#### PostgreSQL TLS Rotation
1. Copy new certificate files to the server volume:
   ```bash
   cp /path/to/new-server.crt /var/lib/postgresql/data/server.crt
   cp /path/to/new-server.key /var/lib/postgresql/data/server.key
   chmod 600 /var/lib/postgresql/data/server.key
   chown postgres:postgres /var/lib/postgresql/data/server.key /var/lib/postgresql/data/server.crt
   ```
2. Signal PostgreSQL to reload configuration without restarting the daemon:
   ```bash
   psql -U aegis_admin -d aegis_db -c "SELECT pg_reload_conf();"
   ```
3. Verify TLS handshake presents new certificate fingerprint:
   ```bash
   openssl s_client -connect postgres.internal:5432 -starttls postgres -showcerts </dev/null 2>/dev/null | openssl x509 -noout -fingerprint -sha256
   ```

#### Redis TLS Rotation
1. Update mounted TLS certificate and key paths in `/etc/redis/tls/`.
2. Issue Sentinel or config rewrite:
   ```bash
   redis-cli -p 6379 --tls --cacert /etc/aegis-tls/ca.crt CONFIG SET tls-cert-file /etc/redis/tls/redis.crt
   redis-cli -p 6379 --tls --cacert /etc/aegis-tls/ca.crt CONFIG SET tls-key-file /etc/redis/tls/redis.key
   ```

#### OpenSearch TLS Rotation
1. Update certificate files in `/usr/share/opensearch/config/`.
2. Execute the OpenSearch Security admin script to reload security configuration:
   ```bash
   /usr/share/opensearch/plugins/opensearch-security/tools/securityadmin.sh \
     -cd /usr/share/opensearch/config/opensearch-security/ \
     -ks /usr/share/opensearch/config/admin-keystore.jks \
     -ts /usr/share/opensearch/config/truststore.jks \
     -nhnv
   ```

## 2. SOP 2: Linux Endpoint Quarantine & Containment

### 2.1 Scope
Applies to automated or operator-initiated endpoint quarantine via `aegis.endpoint_firewall.LinuxContainment`.

### 2.2 Isolating an Endpoint (Quarantine)
1. Trigger isolation via SOAR API or CLI:
   ```bash
   aegis-agent contain --controller-ip 10.0.1.50 --controller-port 8443
   ```
2. Verify active kernel containment:
   ```bash
   sudo nft list table inet aegis_containment
   ```
3. Verify network behavior:
   - Loopback traffic (`ping 127.0.0.1`) must respond.
   - Controller connectivity (`curl -k https://10.0.1.50:8443/health`) must succeed.
   - Outbound internet / corporate lateral traffic (`ping 8.8.8.8` or internal IPs) must be dropped immediately.
4. Verify signed receipt generated by agent and posted to SOAR controller.

### 2.3 Releasing an Endpoint (De-quarantine / Rollback)
1. Trigger release via SOAR controller:
   ```bash
   aegis-agent uncontain
   ```
2. Verify kernel table deletion:
   ```bash
   sudo nft list table inet aegis_containment
   # Expected output: Error: No such file or directory; Table 'inet aegis_containment' does not exist
   ```
3. Emergency Manual Flush (if agent process crashes during containment):
   ```bash
   sudo nft delete table inet aegis_containment
   ```

## 3. SOP 3: Multi-Worker Soak & Load Testing

### 3.1 Scope
Applies to long-duration stress, concurrency, and leak validation using `scripts/soak_test.py`.

### 3.2 Running the Soak Test
1. Set database connection strings and environment:
   ```bash
   export AEGIS_DATABASE_URL="postgresql+asyncpg://aegis_user:secret@localhost:5432/aegis_db"
   ```
2. Start the harness (example for 4 workers, 100 EPS, 24 hours):
   ```bash
   python scripts/soak_test.py \
     --workers 4 \
     --duration 86400 \
     --rate 100 \
     --checkpoint-interval 60 \
     --output local-data/soak_results.json \
     --checkpoint-file local-data/soak_checkpoints.json
   ```
3. Live Monitoring:
   - Inspect `local-data/soak_checkpoints.json` using `tail -f` or jq:
     ```bash
     tail -n 20 local-data/soak_checkpoints.json
     ```
   - Watch memory RSS of worker processes.
4. Verification:
   - Confirm 0 errors reported in `local-data/soak_results.json`.
   - Confirm HMAC audit chain verification succeeded across all participating tenants.

## 4. SOP 4: Encrypted Database Backup & Cold Disaster Recovery

### 4.1 Scope
Applies to database backup creation, cryptographic encryption envelope generation, and cold restoration via `aegis/backup_crypto.py`.

### 4.2 Creating an Encrypted Backup
```python
from aegis.backup_crypto import create_encrypted_database_backup

backup_path = create_encrypted_database_backup(
    db_source_path="/var/lib/aegis/production.db",
    backup_dest_path="/backups/aegis_prod_20261020.agbk",
    passphrase=os.environ["AEGIS_BACKUP_PASSPHRASE"],
)
```

### 4.3 Cold Disaster Recovery Procedure
1. Provision fresh, empty host / container with target database path `/var/lib/aegis/restored.db`.
2. Execute cold restoration:
   ```python
   from aegis.backup_crypto import restore_encrypted_database

   restore_encrypted_database(
       backup_path="/backups/aegis_prod_20261020.agbk",
       target_db_path="/var/lib/aegis/restored.db",
       passphrase=os.environ["AEGIS_BACKUP_PASSPHRASE"],
   )
   ```
3. Verify restored data integrity:
   - Schema and table row counts match pre-incident metrics.
   - Execute audit verification CLI:
     ```bash
     aegis-admin verify-audit --tenant-id all
     ```
   - Confirm 0 broken chains or tampering alerts.
4. Switch application connection strings to point to the restored database instance.

## 5. SOP 5: Incident Response & Tamper Recovery

### 5.1 Broken Audit Chain Alert
- **Symptom**: `verify_audit()` returns `is_valid=False` or points to an invalid sequence index.
- **Immediate Action**:
  1. Freeze database write access for the affected tenant.
  2. Snapshot the current database state for forensic analysis.
  3. Identify the last cryptographically valid sequence number $N$.
  4. Compare records $N$ and $N+1$ against WAL logs to detect unauthorized UPDATE/DELETE operations.
  5. Recover the corrupted audit table partition from the latest verified `AGBK` backup.

### 5.2 Corrupted Backup Rejection
- **Symptom**: Restore fails with `BackupDecryptionError` or `BackupIntegrityError: Plaintext SHA-256 checksum mismatch`.
- **Immediate Action**:
  1. Do NOT attempt to force-read corrupted database bytes.
  2. Inspect storage access logs (S3 CloudTrail or GCS Audit Logs) to check if the backup object was overwritten or altered.
  3. Retrieve the next latest backup version protected by Object Lock WORM retention.
